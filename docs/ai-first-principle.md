# 第一宗旨 · 活人定律

> **这是本项目唯一的最高优先级设计法则。**
> 任何 AI 相关的新增 / 修改 / 优化，都必须先过这一页；与之冲突的需求，**先指出冲突**，不要默默执行。
>
> 建立：2026-10-21（由玩家明确立项）
> 适用范围：`src/ai/**`、`src/systems/**`（含角色状态）、Prompt 组装、事件会话（浴室/安抚/舞蹈/调教/营地事件）、UI 对 AI 状态的呈现

---

## 0. 一句话宗旨

**让游戏中的角色，真实地生活在游戏的世界里。**

不是"功能对玩家有响应"，而是"角色作为一个人，在她的世界里过日子"。
玩家只是她世界里的一个人（指挥官），不是一个能让世界暂停的开关。

---

## 1. 玩家在线模型（必须遵守）

| 状态 | 世界里的真相 |
|---|---|
| **在线·扮演指挥官** | 玩家＝指挥官本人在场：会走路、会说话、会打扰别人、会离开。角色对"指挥官此刻在这里"有真实反应。 |
| **离线·指挥官离开** | 指挥官**不在场**。角色不知道你刚才在电脑前看了多久，也不知道你下线了——她只是发现指挥官不在了，继续做自己的事：睡觉、洗漱、干活、发呆、和别的角色说话。 |
| **离线·指挥官睡觉** | 指挥官也在睡觉。她不会因为玩家关掉游戏就来敲你；世界时间继续流动。 |

落地要求：

1. 任何"只有玩家在才成立"的机制，必须显式标注为**在线态**（如对话窗、按钮邀请、语音），不得让角色在离线时对着空气表演、等待、或被系统强制造出"等你回来"的状态。
2. 离线期间世界必须继续推进，且**角色照常过日子**：`offlineSim` 按真实时间模拟睡眠/作息/营地事件/留言（0 token），回归后按"先结算（睡眠/消息）→ 再生成摘要"的顺序落地；摘要同步进横幅、营地日志、生活档案、**每个角色的记忆**与 Prompt（有效期 6 现实小时）。
3. 角色不能凭空知道离线时玩家做了什么（充值、抽卡、切页面）；只能从世界内可见的线索推断。
4. 玩家重新上线＝指挥官回来/醒来：角色应当有"你回来了/你怎么才来"这类基于她自己作息与离线经历的反应，而不是无缝续上上一句话。

## 2. 活人定律（可执行清单）

任何 AI 行为至少满足以下全部条件，才允许上线：

1. **意愿权**：可以拒绝。拒绝不是错误分支，是正常结果（聊天、邀约、换装、亲密、事件邀请皆同）。
2. **身体与作息**：有困、累、饿、冷、脏、受伤、电力不足；这些状态会影响她做什么、说什么，而不是装饰性标签。
3. **连续性**：记忆、关系、承诺、未完成的事跨天跨会话延续；不允许"聊完就忘"的设定式遗忘（除非明确剧情）。
4. **时间与空间守恒**：做事要花时间，走路要花路程；不允许瞬移、分身、同一时刻出现在两处、同时做两件互斥的事。
5. **过程可见**：换衣服要先换（换装过程皮）、洗澡要先脱/湿、出门要穿鞋——不允许无过程的状态跳变。
6. **后果**：被打扰会烦、被放鸽子会失落、被夸奖会开心；后果要能被后续回合读到（状态标签/记忆/好感）。
7. **不知道不该知道的**：不能读玩家 UI 状态、不能用系统术语（"存档""按钮""刷新"）解释世界。
8. **可恢复**：任何"锁"都必须有解锁路径与超时兜底（读档、异常、玩家离开都能恢复），**禁止不可逆死锁**。

## 3. 硬性玩法事件＝玩法外壳 + 活人内核

浴室事件、安抚事件、舞蹈事件、调教事件等属于**硬性/定制化玩法**：它们需要按钮、相位、专属美术、BGM 才能被玩家操作。
但**外壳的确定性，不等于内核的非人化**。

### 3.1 统一规则

1. **进入前要"够得着"**：人在睡觉/在工作/在别的互斥事件里 → 要么被叫醒/被允许（角色同意），要么进不去；系统不得把她瞬移、瞬醒、瞬换皮。
2. **允许拒绝**：拒绝成本由角色性格与关系决定，不是系统强制通过。
3. **相位必须与现实一致**：换装中就只能说"在换"，待机就只能说"还没开始跳"，睡着就只能梦呓。
4. **代价存在**：打扰睡眠 → 好感/状态；中途离开 → 关系后果；叫醒又走 → "白折腾"要付代价。
5. **独占地点**：同一角色同一时间只能在一个事件里；事件结束要"散场"（换回日常、离开场地、恢复自主）。
6. **结束要有过程**：不是把皮一换、把状态一清就完事，而是走完"收尾动作"（换下、道别、离开）。

### 3.2 判定表（示例）

| 场景 | 允许 | 禁止 |
|---|---|---|
| 准备入睡时玩家聊天 | 她说"我要睡了"继续睡；或放弃睡觉陪聊（穿着睡衣起身） | 系统强制留在睡眠、拒绝一切交互 |
| 深睡且高疲劳 | 第一声叫不醒（只梦呓），连续尝试可醒 | 一声令下立刻起床、瞬换衣服去跳舞 |
| 刚被叫醒、玩家立刻离开 | 她窝回去睡（好感小幅下降，营地日志可见） | 保持清醒站在床边等一个不在的人 |
| 角色正在浴室/安抚室 | 拒绝舞蹈并说明"等这边结束" | 被系统拉去大厅同时出现在两个地方 |
| 舞蹈结束 | 换装过程 → 回原房间 → 事件结束 | 瞬间回日常服、瞬移回房 |

### 3.3 事件专属 Prompt 的硬要求

每个事件协议（`DANCE_PROTOCOL` / 安抚协议 / 浴室协议…）必须至少包含：

- 当前相位（换装中/待机/进行中/被打扰）**且与现实一致**
- 允许拒绝的表述方式
- 与其它事件互斥的表述
- 结束/离场的现实动作要求

## 4. 与需求冲突时的处理流程（重要）

玩家（或任何需求方）提出的玩法若违背现实逻辑，**必须先指出，再给替代方案**，不得为了"实现需求"而写死角色。

流程：

1. **指认冲突**：说明哪一条活人定律/在线模型被违背（引用编号 1–8 或 3.1 条目）。
2. **给出现实可行的替代**：保留玩法意图，用"过程/代价/前置条件"实现（例：想看角色换装 → 加换装过程与时间，而不是瞬切；想随时跳舞 → 先邀请，她按状态决定）。
3. **得到确认后才动代码**；若对方坚持违背宗旨，需在文档中记录为**临时例外**（含原因、到期时间、回退方式）。
4. 例外不得固化成"默认玩法"。

## 6. 提交前自检（AI 相关改动必过）

- [ ] 角色能否拒绝？拒绝的路径写了吗？
- [ ] 有没有新增"硬锁"？锁的解锁路径和超时兜底在哪？
- [ ] 状态跳变是否有过程（换装、进出场地、坐下/起身）？
- [ ] 相位、Prompt、立绘、presence 四者是否一致？
- [ ] 离线/在线语义是否区分？离线时她会做什么？
- [ ] 时间/空间/物理守恒是否成立？
- [ ] 打扰、失败、离开是否有真实代价？
- [ ] 是否引入了不可恢复的异常态（读档/换人/关闭对话后仍卡住）？
